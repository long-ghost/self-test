# 功能自测

> 自包含说明：不支持 skill 机制的工具会把它当普通 Markdown 读，正文已写清触发条件与用法。
> **详细规则在 `references/`，按需加载，不要一次全读**——正文只保留流程骨架和硬约束。

## 什么时候用 / 不用

**用**：功能刚做完，用户说「开始自测」「自测一下」「跑一轮自测」「帮我验一下这个功能」「这个需求做完了，测测」「测试一个模块」「模块测试」。

**模块测试默认包含功能测试与接口测试**：功能按页面/业务闭环验，接口按返回码、业务码、字段、空结果、越权验。只做静态或只做页面、没打接口时，必须在报告「未覆盖」写明原因并降档，不许把模块测试做成单点页面检查。

**不用**：改了两行的小修；只问代码怎么写；排查单个报错（那是调试）。

**开测前先问档位**：L1 / L2 / L3 / L4 四选一，问清再开测，**不默认 L1**。用户已经说了档位则照办，不要重复问；只有连测什么范围都没说清时才连范围一起问。L2 / L3 涉及编译、起服务、开浏览器，需用户明确授权；L4 另需同时授权**开浏览器、调用外部模型、写 `e2e/midscene`**。项目约定 AI 不自行编译或启动服务时，以项目约定为准。

**有独立 agent 就先派**：安装 `agents/module-test-runner.md` 后，主会话不自己上手，按「派谁执行」一节的规则把活交出去（R-22）。

## 首次使用：先初始化

新环境第一次使用，先运行 `scripts/init-workspace.ps1`：

- 自动探测项目根、语言/工程文件、常见环境配置、规则文件；能探测的写入 `references/project-profile.md` 草稿并标 `AUTO-DETECTED`，探测不到的保留占位符。
- 从 `references/test-accounts.example.csv` 复制出 `references/test-accounts.csv`，姓名/电话/密码写 `REPLACE_ME`；**真实账号密码必须由使用者本地填写，脚本不会编造**。
- 从 `code-owners.example.json` 生成 `references/code-owners.json` 草稿；有 `CODEOWNERS` 或 git 历史时可生成建议值。
- 生成 `references/setup-status.md`，列出已探测项、待填项、缺失后影响的档位。

**首次运行门禁**：`references/project-profile.md` 或 `references/test-accounts.csv` 不存在时，L2 / L3 直接停下并打印缺失清单；L4 另需 Node / pnpm / 全局 runner / 模型 Key / `E2E_ROOT/e2e/midscene/suite.json`（默认 `<项目根>/E2E测试/`），缺一即停；L1 可继续，但必须声明未配置项目适配层。未安装 `agents/module-test-runner.md` 时提醒安装；不安装则按 R-19 降级并声明结论上限。

## 安装与更新

技能自身通过 Git 安装（缓存 clone + 同步到技能目录），安装记录在 `<技能目录>/.install.json`。脚本在本目录 `scripts/`，装好后可直接跑：

| 场景 | 命令 | 退出码 |
|---|---|---|
| 首次安装 / zip 安装接管 | `install.ps1` | 0 成功 / 1 失败 |
| 检查更新（只读，不改文件） | `check-update.ps1` | 0 已最新 / 2 有更新 / 1 出错 |
| 执行更新 | `update.ps1` | 0 成功 / 1 失败 |

```powershell
powershell -NoProfile -File "<技能目录>\scripts\check-update.ps1"
powershell -NoProfile -File "<技能目录>\scripts\update.ps1"
```

- **不主动检查**：只有用户明确说「检查更新」「看看有没有新版本」时才运行 `check-update.ps1`。开测前、复盘中、定时任务里都不要自动检查。
- 有更新**先告知用户**，由用户决定是否升级；升级只在两轮之间做，**自测中途不升级**（与「禁止自测中途改技能」同一条约束）。
- 更新会保留 4 个本地配置（`project-profile.md` / `test-accounts.csv` / `code-owners.json` / `setup-status.md`），其余文件以仓库为准，本地多出的文件会被删除。
- 已改过的独立 agent 不会被覆盖，新版本写入 `module-test-runner.md.new`，由用户决定是否替换。
- `check-update.ps1` 需要网络访问 Git 远程；离线环境跳过并在报告里注明「未检查更新」。

## 先承认它会漏（同模型自测的结构性问题）

**同一个模型写完代码再自测，一定会漏，这是结构性的，不是态度问题。** 三种失效：从实现倒推期望、对异常事后合理化、挑容易验的验（难验的塞进「未覆盖」）。

流程约束能压住前两种，**压不住第三种** —— 它不需要违反任何规则，只需要在拆验收点时「想不到」。

五道对冲，缺哪道都要在报告里写明：

| 对冲 | 做法 | 防什么 | 成本 |
|---|---|---|---|
| 换执行者 | 派 `module-test-runner` agent（独立上下文 + 可指定不同模型） | 全链条同源偏差（最彻底，但有边界） | +50%~100% token |
| 换上下文 | 没有可用 agent 时，自测新开会话，只带需求与 `git diff --stat` | 从实现倒推期望 | ≈0 |
| 换判据 | 能写成断言的一律断言并真跑（R-20） | 事后合理化（机器输出不给模型调和空间） | +5~15 min |
| 反证 pass | 对已判 PASS 的条目主动构造反驳并执行（R-21） | 「看起来没问题」 | +5~10 min |
| 豁免配额 | 判「正常」的豁免每轮 ≤3 条，超出记缺陷 | 大面积合理化 | 0 |

**结论强度据此收窄**（取最低者）：

| 执行形态 | 结论上限 |
|---|---|
| 派独立 agent（新上下文 + 独立判定） | 「通过」 |
| 新会话自测 | 「通过」 |
| 同一会话内写完代码接着自测 | 「有条件通过」 |

**换执行者不是万能药**：它砍掉「同源记忆」和「同源推理习惯」，砍不掉「共同知识盲区」和「需求本身缺失」——两个模型都不懂的业务口径，换谁都会漏。所以它排在「换判据」之前只是性价比问题，**不能替代 M1/M2 断言**。

**不要假装流程能消除偏差** —— 报告里不许出现「已独立验证自我实现」这类话。

失效机制、判据分级（M1/M2/M3）、盲采集、反证 pass 操作步骤、做不到的事，见 `references/independence.md`。

## 派谁执行（R-22）

**优先派 `module-test-runner`**（安装位置 `~/.codebuddy/agents/module-test-runner.md`，本机全局）。它拥有独立上下文、独立证据链、独立判定权，主会话不再复判它的结论。

- **派活方（主会话）只做三件事**：确认档位、给出范围（`git diff --stat`）、转达产物目录。**不要把自己的实现说明、自测草稿、验证结论塞给它**，那等于把污染源一起递过去。
- **它返回的是最终判定**。主会话觉得它判错了，只能补一条「主会话异议」写进报告末尾，**不许直接改它的结论或等级**。
- **你要自己就是 `module-test-runner` 时，不要派子 agent**，也不要再找一个「独立判定者」——你就是那第二双眼睛。
- **兜底**：agent 不可用 / 超时 / 失败时，主会话自己按七步执行，**结论上限降为「有条件通过」**，并在首部声明「独立 agent 不可用，已降级」。不许悄悄跳过。

agent 的模型当前用默认（与主模型相同），因此**同源推理盲区仍在**。要真正换视角，在 frontmatter 的 `model` 里改成不同厂 / 不同代的模型——同系列换档位只是变笨，不是变独立。

## 执行契约（缺一条即视为未执行本技能）

### 七步，每步有可检查的产出

| 步 | 动作 | 产出物 | 落在报告 |
|---|---|---|---|
| 1 | 定档 + 定范围 + 判模块类型 | 三句话 | 首部 |
| 1.5 | 用户口述需求 + 与文档对齐 + 冲突交用户裁决 | 需求确认表 + 用户确认时间 | 首部 / `cases.md` 头部 |
| 2 | 拆五层验收点 | 验收点表 | 第二节 |
| 3 | 按方法设计用例 + 期望值前置 | `cases.md` 冻结（含期望来源）+ 用例数 + SHA256 记入报告 | 第二节标题 |
| 4 | 执行（静态 / 接口 / 无头 UI / L4 Midscene 套件） | 命令与输出 | 每条结论的证据列 |
| 5 | 链路三验 + 规范六类 | 三张表 + 规范表 | 三~六节 |
| 6 | 复原、清理、反证 pass、生成缺陷记录、跑自检脚本 | 复原校验 + `git status` + 反证表 + `bugs.xlsx` / `zentao_bugs.json` + 脚本 PASS | 十、十一、十二、十三、十四节 |
| 7 | 复盘 | `EVOLUTION.md` 追加一条（四类标签） | 不进报告，写技能目录 |

**第 6 步追加动作：`report.md` 定稿后生成 HTML 视图**（管理者 30 秒看结论与缺口，可下钻 23 项明细）：

```powershell
python <技能目录>\scripts\report_html.py --report "<产物目录>\report.md" --cases "<产物目录>\cases.md" --bugs "<产物目录>\bugs.json" --out "<产物目录>\report.html"
# L4 追加 --l4 "<产物目录>\l4\l4-summary.json"
```

无缺陷时省略 `--bugs`，非 L4 省略 `--l4`。`report.md` 仍是 `check-report.ps1` 的机器校验底稿，HTML 只是附加阅读物，不替代十四节结构。

**时序硬约束（独立性）：第 1 步只看 `git diff --stat` 与文件名；第 1.5 步必须让用户口述需求并完成冲突裁决，未确认不得进入第 2 步；第 2~3 步只读需求、plan、规范、库表；`cases.md` 落盘且哈希记入报告之后，第 4 步才允许开页面与打接口。先看实现再写用例，写出来的只是实现的说明书。**

**七步全部由执行者一个人完成**；派活方只确认档位、给范围、转达产物目录，不参与判定（R-22）。

**盲采集（R-20）：第 4 步采集实测值时仍不许读源码**（`.vue` `.ts` `.java`），字段名从接口返回、表结构、需求里拿。判定写完才允许读源码定位根因，**读过源码的条目在证据列标「已读源」，M2 / M3 判定降一档**（M1 是机器给的结论，不受影响）。**

**任一步产出缺席 = 本轮未完成，不许写「通过」。**

### 二十八条硬规则（报告逐条给结论）

| 编号 | 规则 | 判定依据 |
|---|---|---|
| R-01 | 仓库只读，不改任何代码 | `git status` 只含已忽略的产物目录 |
| R-02 | 写库必须复原 | 行数一致 + 被改行逐字段比对一致 |
| R-03 | 需求来源标注 | 首部写明 原文 / plan 推导 / 口述 |
| R-04 | 五层验收点齐全 | 功能 / 流程 / 数据 / 逻辑 / 规范 各 ≥2 条 |
| R-05 | 用指定方法设计用例 | 用例表有「方法」列，不是单一方法包打 |
| R-06 | 覆盖度三指标 | 需求 100%、边界字段 100%、组合成对 |
| R-07 | 分层约束一致性 | 前端 / 接口 / 数据库 三方对比矩阵 |
| R-08 | CRUD 按模块能力全量 | 有写操作则逐项；只读则给判定依据 |
| R-09 | 链路三验 | 流程闭环 / 数据血缘 / 业务逻辑 各一张表 |
| R-10 | 规范六类核对 | 配色 / 交互 / 下拉 / 列表 / 图表 / 输入框 |
| R-11 | 结论必须有证据 | 命令、退出码、输出片段、截图或代码行号 |
| R-12 | 未覆盖项说明原因 | 第九节逐条 |
| R-13 | 不改共享文件、不自建工具链 | 无新增脚本 / CI / 基线文件 |
| R-14 | 浏览器优先无头 | 启动参数含 `--headless=new` |
| R-15 | 账号优先查本机账号表，其次查库 | 有 `references/test-accounts.csv` 选号记录或 SQL 记录；密码不进报告/产物，转发技能前必须脱敏导出 |
| R-16 | 期望值前置，不许事后回填 | 用例表有「期望来源」列；期望在执行前落盘；实际≠期望时先定性，不覆盖原期望 |
| R-17 | 独立判定，举证责任在「判正常」一方 | 依据只落在 需求 / plan / 规范条款 / SQL 反算 / 已知基准 / 口述；判「正常」必须引出处在证据列；不得以源码、类名、行号为据 |
| R-18 | 用例冻结后才准执行 | `cases.md` 先落盘 → SHA256 前 16 位写进报告首部 → 才允许第 4 步；收尾复核哈希一致，不一致即本轮作废 |
| R-19 | 上下文隔离分级 | 首部声明「新会话 / 同会话」；同会话自测结论最高「有条件通过」，不许写「通过」 |
| R-20 | 判据分级，能断言必断言 | 判定列标 M1 / M2 / M3；M1 有真跑的命令与输出；每条断言配负例；M3 占比 ≤30%；关键结论双源 |
| R-21 | 反证 pass 留痕 | 十三节 ≥3 条已判 PASS 被主动构造反驳并真执行，含假设与否定证据 |
| R-22 | 优先派独立 agent 执行 | 有 `module-test-runner` 时由它出结论，主会话不复判；不可用才降级自测，且首部声明降级、结论上限「有条件通过」 |
| R-23 | 缺陷必须落单 | 每条 P0~P3 都生成 `bugs.json` + `bugs.xlsx` + `zentao_bugs.json`；字段含标题/等级/类型/模块/复现步骤/期望/实际/截图或接口地址/责任人；只写报告第七、八节 = 未完成 |
| R-24 | 责任人可追溯 | 顺序：用例指定 → `references/code-owners.json` → `git log/blame` → 「待确认」；禁止臆造姓名，禁止把「待确认」写进禅道 `assignedTo` |
| R-25 | 禅道写入安全 | Excel/payload 不含密码、token、cookie；`--zentao` 只从环境变量取凭证；无禅道环境时 Excel 为唯一交付，不许假装已写入 |
| R-26 | 能测必测 | 账号可用、控件可达、入口可导航、数据可通过换参数或合法造数复原触发的项，必须亲自执行；禁止「相邻分支已验证」「接口层验过等于页面验过」「按钮存在等于弹窗验过」 |
| R-27 | 未覆盖举证 | 每条未覆盖必须写 `[尝试] [证据] [原因] [补测]` 四要素，缺任一视为未完成；能力内未测不得写「通过」 |
| R-28 | 需求手写优先 | 必须先请用户用自己的话手写业务逻辑（不要求写全、不许 AI 代写或文档勾选代替）；与文档冲突时以用户手写为准，用户未写处才看文档并标「文档补充」，二者都没有才返回用户裁决；未确认不得冻结用例或开测 |

**不适用的规则必须写依据**（例：R-08 不适用——模块只读，Controller 仅 GET）。留空等于没做。

### 收尾自检（自己跑，不交给用户）

```powershell
& "<技能目录>\scripts\check-report.ps1" -Report "<产物目录>\report.md"
```

脚本查结构（章节、R 清单、用例数、覆盖数、期望来源列、`cases.md` 存在与哈希一致、期望来源白名单、源码引用、空单元格、截图是否存在）。**FAIL 就改到 PASS，不许带着 FAIL 交付，也不必把 FAIL 过程贴给用户——用户只看 bug。**

脚本管结构，五条内容必须人工确认：

1. 证据能复核：命令能重跑、截图能打开，不是「已确认」三个字
2. 五层里没有凑数行（写了但不构成可判定行为）
3. 阻塞项没被降级成建议项
4. 数据复原是真跑过，不是照计划抄的
5. 十三节的反证是真跑的：假设具体、手段产生过新信息、至少一条换源重算

## 自主调查优先（默认不问）

能自己查明白的一律自己查。只有四类允许停下来问：**档位未指定**（开测前的 L1/L2/L3/L4，见「什么时候用 / 不用」）、**口径要拍板**、**要动共享文件**、**拿不到的外部条件**（密码、写库授权、只有业务方能定的「这个数对不对」）。L4 另需单独确认「外部模型调用与用例目录写入」。档位之外的事项问之前，必须先查过并带上结论。

查证入口：接口签名看 Controller/DTO；表结构与数据用数据库 MCP 或 CLI；口径自己写 SQL 算一遍再和页面比；页面行为用浏览器 eval 或直接打接口；历史原因用 `git log -S` / `git blame`；规范看项目规则文件与 `<project-rules>/`；账号查项目用户表 / 部门关系表。

真要问，必须带：已查过什么（附结果）→ 我倾向哪个 → 为什么。不许把纯选择题推回去。

## 七步怎么做（第 7 步复盘见下一节）

### 1 定档 + 定范围

| 档位 | 做什么 | 耗时 | 能证明 / 证不了 |
|---|---|---|---|
| L1 | 不启服务：契约比对、字段链路、SQL 脚本、typecheck、构建、UI 规则代码级核对 | 2~5 min | 代码自洽；证不了交互 |
| L2 | 启后端打接口：返回码、业务码、字段、空结果、越权 | 5~15 min | 后端行为；证不了页面 |
| L3 | 前后端 + 无头浏览器 + 截图 | 15~40 min | 端到端 |
| L4 | Midscene Test：真实浏览器 + YAML 用例 + AI 断言，可沉淀到 `e2e/midscene/` | 20~60 min | 可复用的端到端行为；AI 断言按 M3，数值 / 权限必须另有 M1/M2 |

范围默认 = 本次 `git diff` + 最近相关 plan；**工作区干净时必须问清测哪次改动**，不能默认「最近一次提交」。

模块类型（只读 / 单表 CRUD / 主子表 / 带审批）决定用例规模，判定方法见 `references/crud.md`。

### 1.5 需求确认（冻结前硬门槛）

1. 读需求原文 / plan / 页面 README / 规范，只读「做什么」段落，不读实现；**文档只作为对齐参考，不代替用户口述**。
2. **必须请用户用自己的话手写本轮业务逻辑**（不提供选项、不许 AI 代写、不许拿文档条目让用户勾选）：测什么业务、谁用、期望行为、明确不测什么。不要求写全——用户写了多少算多少。
3. **优先级规则（用户裁决，2026-11-26）**：
   - 用户手写逻辑与需求文档冲突时，**一律以用户手写逻辑为准**，不需要再让用户二选一裁决；
   - 用户手写逻辑没写到的部分，才看项目原本的需求文档，按文档补齐并标注「文档补充」；
   - 文档缺失、且用户也没写的部分，才返回用户裁决。
4. 生成需求确认表：条目 / 文档依据 / 用户手写原话 / 状态（一致 / 冲突-以用户为准 / 文档补充 / 文档缺失待裁决）/ 本轮生效版本 / 来源标注（用户手写 / 文档补充 / 用户裁决）。
5. 全部确认后，把「本轮生效需求」写进 `cases.md` 头部，并在报告首部写 `**需求确认**：用户已确认（YYYY-MM-DD HH:mm）`、`**口述来源**：用户手写 N 条 / 文档补充 M 条 / 裁决 K 条`。
6. 文档缺失且用户未写、需要拍板才继续时：停下，返回缺口清单（附带「按现有文档推断」的建议），不生成 `cases.md`、不冻结、不开页面、不打接口。

**主会话派活时不得把自己的需求理解、文档摘要塞给 agent 当「用户口述」**；agent 拿到的是「用户手写原文 + 文档参考」两栏，冲突处按第 3 条自动以用户手写为准（R-28）。检查脚本会拦截「用户口述」列全是文档勾选、没有用户手写原话的报告。

### 2 拆验收点

找需求来源（优先级）：`docs/requirements/<user>/` → `docs/plans/<user>/` → 页面 `README.md` → 用户口述。**只使用第 1.5 步已由用户确认的本轮生效需求**，未确认项不得写进验收点。

输出五层验收点表（功能 / 流程 / 数据 / 逻辑 / 规范，每层 ≥2 条）。**第 1.5 步确认完成后才拆验收点**；不得再自行变更需求口径。原文缺失按 plan 推导时，必须已在需求确认表中由用户确认。

用例怎么设计（等价类、边界值、判定表、状态迁移、场景法、成对组合、错误推测、数据对账、权限矩阵）：读 `references/methods.md`。

**期望值前置（硬要求，借 TDD 的「先写失败断言」）**——每条用例的期望值必须在执行前写死，四条：

1. **写得出期望才算设计完**：期望值必须标来源。写不出期望的用例不成立，回去补需求，不许「先看看页面是什么样」。
2. **先冻结再执行**：用例写进 `cases.md`（格式见 `assets/cases-template.md`），算 SHA256 前 16 位写进报告首部，之后才允许动第三~六节。执行中才发现的验收点追加到 `cases.md` 末尾并标「新增」，更新首部哈希并在报告备注。
3. **依据不许落在源码上**：期望来源只能是 **需求原文 / SQL 反算 / 规范条款 / 已知基准 / 用户口述**。只能引源码（类名、方法、行号、`.java` `.vue` `.ts` 路径）才成立的验收点，不是验收点——删掉，回去确认需求。
4. **不许回填**：实际值与期望不符时第一动作是定性——是 bug，还是期望写错。判 bug 原样保留；判期望写错，**保留原期望 + 并列写更正依据**，不许直接覆盖成实际值。

**举证责任倒置**：实际与需求不符时**默认记缺陷**。要判「正常 / 设计如此」，必须在证据列引出需求原文或规范条款；引不出出处就记缺陷（P3 起步）。「代码里就是这么写的」不构成依据。

数据对账类用例强制此顺序：**先写 SQL 算出期望数 → 再打开页面比对**，禁止反过来。

## 反证 pass（收尾必做，R-21）

判定全部写完、结论还没落笔之前，**先攻击自己**。这一步是整份技能里唯一专门用来对付「自己看不出问题」的动作，不许省。

**选样**（≥3 条，从已判 PASS 里挑）：所有 M3 条目 → 证据只有截图或单源的 → 靠「设计如此」「跟别处一致」判正常的 → 涉及计算 / 权限 / 状态的。

**每条四行**：

```
假设：这条如果其实错了，最可能错在哪？（≥2 种，具体到可验证，不许写「没有可能」）
手段：用一条新检查验证该假设（必须真执行，不许推理）
结果：假设被否定（留证据）/ 假设成立（转缺陷，重新定级）
证据：命令输出 / SQL / 两次取值对照
```

**硬要求**：

- 假设必须具体到能验：「可能口径算错了」不算；「可能把退款单也算进销售额了」才算
- 手段必须产生**新信息**：换数据源重算、换账号重取、换入口再走一遍。重看同一张截图不算
- 至少一条是「同一数字两个来源重算」，不一致就是缺陷或口径问题
- 假设成立**不许改口说「其实也没关系」**，转缺陷按 P0~P3 定级
- 结果全是否定且无证据 = 没做，重跑

详细判据与反模式见 `references/independence.md`。

## 缺陷记录（每轮必做）

**触发**：模块测试发现任何 P0~P3 缺陷。没有缺陷时报告首部写「缺陷记录：0 条」，不生成文件；有缺陷却只写报告 = 违反 R-23。

**固定动作**：

1. 从 `assets/bug-record-template.json` 复制一份 `bugs.json` 到本轮目录，逐条填缺陷。
2. 跑生成器（脚本在技能目录，不在项目仓库）：

```powershell
python <技能目录>\scripts\bug_report.py `
  --input .codebuddy\selftest\<轮次>\bugs.json `
  --out   .codebuddy\selftest\<轮次>\bugs.xlsx `
  --payload-out .codebuddy\selftest\<轮次>\zentao_bugs.json
```

3. 核对 `bugs.xlsx` 的「缺陷明细 / 禅道导入 / 说明」三个 sheet；责任人「待确认」要在报告里单列数量。
4. 把缺陷编号、等级、责任人、证据路径写进报告第十四节。

**必填字段**：`title`、`severity`（P0~P3）、`type`（功能/接口/数据/规范）、`module`、`steps`、`expected`、`actual`，以及 `screenshot` 或 `api_url` 至少一项。P0/P1 缺复现步骤或证据时不许交付。

**责任人解析（R-24）**：

1. `bugs.json` 显式 `owner`；
2. `references/code-owners.json` 的 `owners` 映射（模块名 / 路径前缀 / glob）；
3. `files` 里的文件跑 `git log -1 --format=%an -- <file>`，有行号时 `git blame -L <line>,<line> -- <file>`；
4. 仍查不到填「待确认」，不许猜。

**禅道映射（R-25）**：

- 等级：P0→1 致命、P1→2 严重、P2→3 一般、P3→4 轻微；优先级同号。
- 类型：功能/接口→`codeerror`，数据→`others`，规范→`standard`。
- `zentao_bugs.json` 是 API/MCP payload；没有禅道环境时只生成 Excel，不假装已写入。
- 真写入需 `ZENTAO_BASE_URL` + `ZENTAO_TOKEN`（或账号密码），凭证只从环境变量读，不写进 Excel/报告/日志。
- 不同禅道版本的 Excel 导入列名可能不同；导入前用目标实例模板核对，对不上就走 API/MCP。

**详细字段、Excel 列、API 端点与 MCP 说明**：读 `references/bug-report.md`。

## 复盘（每轮收尾做）

四个必答，写进技能目录的 `EVOLUTION.md`（append-only）：

| 标签 | 判什么 |
|---|---|
| 漏网 | 本轮缺陷能否套进现有检查项；**套不进 = 漏网，下一轮开测前必须补规则** |
| 空转 | 连续 ≥3 轮不适用的检查项，考虑降级或删 |
| 阻塞 | 命令失效 / 路径变化 / 工具不好用，下次还会再卡 |
| 新知识 | 影响判定的口径或数据结构，不记流水账 |

**禁止自测中途改技能**（标准会漂移），改动一律放在两轮之间。判定方法与合并纪律见 `references/retrospective.md`。

## 判定

**判据只有三级，判定列必须带等级**：

| 等级 | 含义 | 证据形态 |
|---|---|---|
| M1 | 可执行断言，机器给的结论 | 真跑的命令 + 输出片段 / 退出码 |
| M2 | 可复算，第三方能重算出同一个数 | SQL 全文 + 结果，或两处数值对照 |
| M3 | 只能人判（排版、文案、手感） | 截图 + 引用的规范条款 |

- 能 M1 的不许降成 M3：「点一下看到数字对了」不算 M1，把数字从接口或 SQL 取出来比对才算
- M1 必须真跑，命令要能原样重跑出同样结果；断言脚本放 `.codebuddy/selftest/<本轮>/tmp/`，收尾删除
- 每条断言配一个负例（非法输入 / 越权 / 超界必须被拒绝），只验正例 = 自欺
- M3 占比 >50% → 结论最高「有条件通过」
- 数值、权限、状态三类结论要双源，单源在证据列标「单源」
- 没有本轮新鲜证据，不许说通过
- 期望值被实测值覆盖且未留更正依据 → 本轮证据不可信，结论最高只给「有条件通过」
- 禁止措辞：应该、大概、似乎、看起来、基本没问题
- 发现 P0 不要停，跑完再单列（半途停会漏掉其他问题），结论直接判「不通过」
- **L4**：AI 断言一律 M3；数值 / 金额 / 条数 / 权限 / 占比类结论没有 M1/M2 交叉核验，该条上限「有条件通过」；M3 占比仍按现有规则计
- **L4**：模型抖动导致同一用例两轮结论不同，必须写「不稳定」并保留两轮证据，不许只留通过的一轮

**结论强度取三者最低**：档位（L1 静态自洽 / L2 后端行为 / L3 端到端可用 / L4 可复用端到端 + AI 断言）× 执行形态（独立 agent 或新会话 ≤ 通过；同会话 ≤ 有条件通过；agent 降级 ≤ 有条件通过）× 判据构成（M3 >50% ≤ 有条件通过）。

## 报告

用 `assets/report-template.md`，**十四节固定**。头部第一屏必须有：

```
**结论** / **本轮问题**：P0 x / P1 x / P2 x / P3 x（明细见七、八节）/ **范围** / **需求来源** / **需求确认**：用户已确认（YYYY-MM-DD HH:mm）/ **口述来源**：用户手写 N 条 / 文档补充 M 条 / 裁决 K 条 / **测试耗时**：<YYYY-MM-DD HH:mm> → <YYYY-MM-DD HH:mm>（共 N 分钟）/ **执行会话**：新会话 | 同会话（同会话 ⇒ 结论上限「有条件通过」）/ **判据构成**：M1 x / M2 x / M3 x（M3 占比 y%）/ **用例冻结**：cases.md SHA256 <16 位> / **缺陷记录**：bugs.xlsx x 条（责任人待确认 y 条）/ **假设**
```

`测试耗时` 必须写真实起止时间：开始=确认档位与范围，结束=报告定稿；禁止估算或按文件时间倒推。

**L4 报告**：十四节结构不变，另在首部加 `**L4 套件冻结**` / `**L4 执行**` 两行，文末追加「十五、L4 端到端（Midscene）」（格式见 `assets/report-template.md`）。非 L4 报告删除这两行且不出现第十五节，`check-report.ps1` 据此区分。HTML 用 `report_html.py --l4` 生成附加视图。

## 红线

- 不许跳过执行契约：七步产出缺一项即未完成；报告缺「规则命中清单」等同未执行
- 复盘不许只写「无」：漏网 / 空转 / 阻塞 / 新知识四类都要给判断依据
- 自检脚本 FAIL 不许交付，不要把检查工作推给用户
- 不许把自己能查的事拿去问
- 不许只跑功能点就下结论：流程不通、数据对不上、口径算错，一样是不通过
- 自测期间仓库只读，连 typo 都不改
- 期望值不许事后回填，实测值不许拿来当期望
- `cases.md` 冻结后不许回头改期望或删用例；要改只能追加并标「新增」
- 不许以源码、类名、行号作为「本该如此」的依据
- 采集阶段不许读源码；读过源码的条目不许当独立证据（M2 / M3 降档）
- 有 `module-test-runner` 却自己上手 = 违反 R-22；agent 挂了要声明降级，不许静默跳过
- 同会话自测不许声称「通过」，也不许写「已独立验证」
- 反证 pass 不许省：结果全是「假设不成立」且无证据 = 没做
- 判「正常」的豁免超过 3 条，超出部分必须记缺陷
- 发现 P0~P3 缺陷却不生成 `bugs.xlsx` / `zentao_bugs.json` = 未完成（R-23）
- 责任人只许按映射表 / git blame / 待确认三级来，不许猜姓名（R-24）
- 禅道凭证、密码、token、cookie 不许进 Excel、payload、报告、日志（R-25）
- 能力内可执行却写进未覆盖 = 本轮未完成，结论不得高于「有条件通过」；补齐后才允许写「通过」（R-26/R-27）
- 用户未手写业务逻辑、拿文档勾选或 AI 代写当口述 = 本轮未完成（R-28）；手写与文档冲突未以手写为准、或用户未写处未标「文档补充」同理
- 不碰共享文件、不自建工具链
- 不 cd 进 `dist/` / `target/`；不并发编译
- 产物只留报告、截图与缺陷记录（`bugs.json` / `bugs.xlsx` / `zentao_bugs.json`），日志、profile、临时脚本一律删

## 方法论来源（诚实标注）

- 自写：七步流程、执行契约、分层一致性、CRUD 清单、数据策略、产物规则
- 借鉴 `verification-before-completion`：无新鲜证据不许宣称完成、禁「应该/大概」、结论附证据
- 借鉴通用测试方法论：测试金字塔、等价类与边界值、Given-When-Then
- 借鉴 `superpowers` 的 TDD **只取一点**：先写失败断言（红灯）再看实现（R-16 期望值前置）。
  **不引入**红-绿-重构循环、测试代码、覆盖率——自测阶段仓库只读，写测试代码既越界又会削弱独立性
- 不要对外声称本技能是 superpowers 的移植
