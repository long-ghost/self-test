# 独立性与自我确认偏差

本文解决一个具体问题：**写完代码的同一个模型，转头自测自己写的东西，会不会漏？**

答案是会，而且不是「认真一点就能避免」的那种会。本文说明失效机制、能用的对冲手段、以及哪些偏差根本消不掉。

## 一、三种结构性失效

| 失效 | 机制 | 在报告里的样子 |
|---|---|---|
| **实现倒推需求** | 上下文里已有实现，写期望时不是「需求要什么」而是「代码做了什么」 | 用例全落在实现覆盖到的分支上，没实现的需求自然没有用例 |
| **事后合理化** | 实测与期望不符，第一反应是替自己找理由 | 「设计如此」「业务上也可以」「这个不影响使用」「建议项 P3」 |
| **避重就轻** | 挑容易验的验，难验的移进「未覆盖」 | 简单 CRUD 一堆用例，口径计算、权限、并发一句「未覆盖：缺数据」 |

前两种可以靠流程压制（R-16 期望值前置、R-17 举证倒置）。**第三种压不住**——它不需要违反任何规则，只需要在拆验收点时「想不到」。而「想不到」正是同一模型的自洽盲区。

## 二、五道对冲，按性价比排序

| # | 手段 | 成本 | 防得住 | 防不住 |
|---|---|---|---|---|
| 1 | **换执行者**：派 `module-test-runner`（独立上下文，可换模型） | token ×1.5~2 | 全链条同源偏差（同源记忆 + 同源推理习惯） | 共同知识盲区、需求缺失 |
| 2 | **换上下文**：没有 agent 时新开会话，只带需求与 `git diff --stat` | 接近 0 | 实现倒推需求 | 避重就轻 |
| 3 | **换判据**：能写成断言的一律断言并真跑 | 每轮 +5~15 min | 事后合理化（模型无权调和机器输出） | 需求本身漏了 |
| 4 | **反证 pass**：对已判 PASS 的条目主动构造反驳并执行 | 每轮 +5~10 min | 「看起来没问题」 | 系统性盲区（同一模型想不出的假设） |
| 5 | **豁免配额**：判「正常」的豁免每轮 ≤3 条 | 0 | 大面积合理化 | 单条豁免判断错 |

**不要同时省掉 1/2 和 3。** 只做流程（冻结、哈希、白名单）而判据仍是「模型读一遍觉得对」，等于给主观判断加了个时间戳；只换执行者而不换判据，等于让另一个人用同一双模糊的眼睛看一遍。

## 三、判据分级：M1 / M2 / M3

每条用例的「判定」列必须带等级：

| 等级 | 定义 | 允许的证据 | 例 |
|---|---|---|---|
| **M1 可执行断言** | 命令 / 脚本 / 接口输出与期望**逐字或逐值**比对，退出码可查 | 真实执行的命令 + 输出片段 | `curl ... \| jq .code` → `0`；断言脚本 `exit 0` |
| **M2 可复算** | 数值能由第三方重算：SQL 反算、两方对照、状态迁移表 | SQL 全文 + 结果；两处数值 | 页面 8,642,100.00 = `SELECT SUM(...)` |
| **M3 人判** | 只能靠阅读与品味：排版、文案、交互手感、术语一致性 | 截图 + 引用的规范条款 | 表头字号是否与规范一致 |

### 硬约束

1. **能 M1 的不许降成 M3。** 「点一下看到数字对了」不是 M1，把那个数字用接口或 SQL 取出来比对才是。
2. **M1 必须真跑。** 写在报告里的命令要能原样重跑出同样结果；断言脚本放 `.codebuddy/selftest/<本轮>/tmp/`，收尾删除（不入仓库、不提交）。
3. **每条断言配一个负例。** 正向「保存成功」必须搭配一次「非法输入 / 越权 / 超界被拒绝」。只验正例是本技能最常见的自欺形式——`maxlength` 生效不代表后端校验存在。
4. **M3 占比 ≤30%**，超过就在报告首部标出并说明原因；M3 占比 >50% ⇒ 结论最高「有条件通过」。
5. **关键结论要双源**：数值、权限、状态三类，至少两个独立来源（接口 + SQL / 页面 + 接口）。单源条目在证据列标「单源」。

## 四、盲采集：采集与定位分离

现在的时序只规定「用例冻结后才允许读源码」。不够——**读过源码之后，模型给这条用例打的 PASS 已经不可信了**，因为它知道了「代码本来想做什么」。

改成两段：

```
采集段（第 4 步前半）：只从页面 / 接口 / 库三个外部面取值。
  ✗ 不读 .vue .ts .java（哪怕只是「看一眼确认字段名」）
  ✓ 字段名从接口返回值、表结构、需求里拿

判定段：拿实测值与 cases.md 的期望逐条比对，写判定 + 等级。

定位段（仅判为缺陷后）：这时才允许读源码找根因。
  读过源码的条目，在证据列追加「已读源」，该条判定可信度降一档
  （M1 → 仍算 M1，因为断言结果不因读源码而变；M2/M3 → 视为 M3）
```

**为什么 M1 不受影响**：断言是机器给的，读不读源码它都是那个结果。**M2 / M3 受污染**，所以降档。

## 五、反证 pass（收尾必做，R-21）

执行完、判定写完，**不要直接写结论**。先花 5~10 分钟攻击自己。

### 选样

从已判 PASS 的条目里挑 ≥3 条，优先级：

1. 所有 M3 条目（最不可靠）
2. 证据只有一处、或只有截图的条目
3. 判「正常」时引的是「设计如此」「跟别处一致」这类软依据
4. 涉及计算、权限、状态的条目（错一次影响最大）

### 每条写四行

```
假设：这条如果其实错了，最可能错在哪？（列 ≥2 种，不许写「没有可能」）
手段：用一条新检查验证该假设（必须真执行，不许推理）
结果：假设被否定（留证据）/ 假设成立（转缺陷，重新定级）
留痕：写进报告第十三节
```

### 强制要求

- **假设必须具体到可验证**：「可能口径算错了」不算，要写「可能把退款单也算进销售额了」。
- **手段必须真跑**。写「已复核，无误」= 没做。
- **至少一次「换数据源重算」**：同一数字换一条 SQL / 换一个账号 / 换一个入口再取一次，两次不一致就是缺陷或口径问题。
- 假设成立时**不许**改成「其实也没关系」——转缺陷，按 P0~P3 定级。

### 反证 pass 的反模式

| 反模式 | 为什么是自欺 |
|---|---|
| 只挑最稳的 M1 条目反驳 | 必然全部被否定，等于没做 |
| 假设写成「可能没测到」 | 不可验证，无法执行手段 |
| 手段用「重新看了一遍截图」 | 同一双眼睛看第二遍，不产生新信息 |
| 结论全是「假设不成立」且无证据 | 反证与被证伪的自我循环 |

## 六、豁免配额

判「正常 / 设计如此 / 不算缺陷」本质上是在**推翻一条期望**，举证责任在判方（R-17）。再加一条量的约束：

- 每轮豁免 **≤3 条**（同一根因合并计 1 条）。
- 第 4 条起，一律记 P3 缺陷，报告里标注「超豁免配额」。
- 豁免必须写：需求原文引用 / 规范条款编号 / 用户口述时间。**三者都拿不到 ⇒ 不许豁免。**

配额不是形式主义。一轮里出现 6 条「设计如此」，说明要么需求没读透，要么在替自己开脱——两种情况都该让用户看见。

## 七、做不到的事（诚实标注，别在报告里吹）

| 做不到 | 说明 |
|---|---|
| 真正「忘记」实现 | 同会话自测时，实现一直在上下文里。流程只能降低影响，不能消除 |
| 保证覆盖率 | 用例只覆盖「想到了的」验收点。没想到的需求，自测永远发现不了 |
| 证明「没有 bug」 | 自测产出的是**证据强度**，不是正确性证明。结论措辞按档位与判据构成收窄 |
| 消除共同知识盲区 | 换成独立 agent（甚至换模型）后，「两个执行者都不懂这个业务口径」依然成立。换人不换知识 |

## 七之二、独立 agent 能补多少、补不到哪里

本机装了 `module-test-runner`（`~/.codebuddy/agents/module-test-runner.md`）时，第二双眼睛从「建议」变成「默认」：

| 它补上的 | 它补不上的 |
|---|---|
| 不共享开发过程的记忆（最大一块） | 需求本身缺失的验收点 |
| 独立采集证据、独立判定，主会话无权改结论 | 两个模型都不懂的口径 |
| 结构上不能改业务代码（无 Edit 工具 + 提示词约束） | 证据质量本身的问题（错的数据换谁都判错） |
| 不同模型时可降低同源推理习惯 | 同模型时只剩「上下文隔离」这一层收益 |

**所以顺序仍是：换判据（M1/M2）→ 换执行者 → 反证 pass。** 把 agent 当万能药、证据仍靠「看一眼觉得对」，等于花双倍 token 买了个心理安慰。

**降级规则**：agent 不可用 / 超时 / 失败时，主会话自测，结论上限「有条件通过」且首部声明降级。**不许悄悄跳过这一步**——那等于把唯一的结构性对冲关掉还不告诉人。

## 七之三、能力边界判定（能测必测）

「保证覆盖率做不到」只承认**盲区**，不豁免**能力内可执行但未执行**。写第九节前必须把「真的做不到」和「没做」分开：

| 常见说法 | 必须执行的反证动作 |
|---|---|
| 账号可用但本轮未登录 | 用该账号登录一次，再写实测结果 |
| 相邻分支已验证同一逻辑 | 亲自走当前分支，相邻分支证据不能替代 |
| 接口层已验证等于页面已验证 | 回到页面复验同一数值与展示 |
| 仅确认按钮存在 | 点开弹窗，验二次取数与关闭后状态 |
| DOM 未定位到控件 | 检查入口条件、换内嵌入口、查组件定位；仍找不到才写客观限制 |
| 当前库数据非空，空态无法触发 | 换账号 / 年份 / `deptId`，或按 `project-profile.md` 造数并复原后验空态 |

三条判定线：

1. **真的做不到**：有客观条件证据（账号不存在、权限被回收、入口路由下线、环境不可达），并按 `[尝试][证据][原因][补测]` 留痕。
2. **没做**：账号可用、入口可达、数据可构造、控件可换入口定位——一律不算未覆盖，判本轮未完成。
3. **同会话污染**：不要在拆用例阶段就登录/造数；三问在写第九节前应用，执行证据按 R-18 冻结后采集。

**结论强度公式**（取最低者，写进报告首部）：

```
档位：L1 静态自洽 / L2 后端行为 / L3 端到端
× 上下文：新会话 ≤ 通过 / 同会话 ≤ 有条件通过
× 判据：M3 ≤30% 不影响 / >50% ≤ 有条件通过
```

## 八、什么时候升级给人裁决

只有四种，其余自己查：

1. 口径要业务拍板（两周前的定义、两个部门理解不一致）
2. 需求本身矛盾或缺失，且 plan 也没写
3. 反证 pass 里「假设成立但不确定是不是缺陷」
4. 需要动共享文件才能验证（此时只报告，不动手）
