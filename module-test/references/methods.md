# 用例设计方法

验收点回答「测什么」，本文回答「用哪几组数据测」。**凭感觉挑几个值，等于没设计。**

## 九种方法

| 方法 | 什么时候用 | 产出规则 |
|---|---|---|
| 等价类划分 | 字段有取值范围或类别 | 每个有效类 ≥1 条，**每个无效类 ≥1 条** |
| 边界值分析 | 有数值 / 长度 / 时间 / 分页边界 | 每个边界取 `min-1 / min / min+1 / max-1 / max / max+1`；空值、0、负数单列 |
| 判定表 | 多条件共同决定结果（权限、状态、口径折算） | 列条件桩与动作桩，合并等价规则，每条规则 1 条用例 |
| 状态迁移 | 有状态机（审批、单据、订单） | 每条合法迁移 1 条，每个非法迁移 1 条 |
| 场景法 | 业务流程 | 主流程 1 条 + 每个备选流 1 条 + 每个异常流 1 条 |
| 正交 / 成对组合 | ≥3 个可组合筛选（下拉、日期、枚举） | 用 pairwise，**不做笛卡尔积**；高风险组合单独补 |
| 错误推测 | 经验区 | 空值、重复提交、超长、特殊字符、乱序、并发，列清单逐条打勾 |
| 数据对账 | 有 ETL / 报表口径 | 每个关键指标至少一处「源表值 → 页面值」对照 |
| 权限矩阵 | 有角色 / 部门分权 | 角色 × 关键操作，至少覆盖「有权限」「无权限」两格 |

## 边界值取点细则

**数值**：`min-1 / min / min+1 / max-1 / max / max+1`，追加 0、负数、小数、超大值、科学计数法。

**字符串**：空串、纯空格、首尾空格、超长、特殊字符（`% _ ' " \ < > &`）、全角、emoji。

**日期**：月初、月末、跨年、闰年 2/29、时区边界。

**分页**：首页、末页、超页、`pageNum=0` 或负数、`pageSize` 上下限。

## 三层各跑一次（硬要求）

每条边界 / 类型用例都要：**页面输入一次 → 绕过前端直接打接口一次 → 查库确认实际存了什么**。

只在前端点过，等于只验证了 `maxlength` 一个属性，后端注解和数据库列宽完全没碰到。

## 覆盖度三指标（不是「每个方法都全量」）

| 维度 | 要求 | 理由 |
|---|---|---|
| 需求覆盖 | **100%** | 每条验收点至少 1 条用例，一条用例只挂一个验收点 |
| 边界字段覆盖 | **100%** | 凡有限制的字段都走边界，不许只测中间值 |
| 参数组合覆盖 | **不做全量** | 笛卡尔积爆炸，用成对组合压到 10 条上下 |

**算例**：4 个筛选（部门 7 × 年份 3 × 月份 12 × 维度 4 = 1,008 种）→ 成对组合 12~15 条 + 高风险 4~6 条。

**用例量估算**：`20 个验收点 → 60~90 条`。一轮只有十几条，基本就是只跑了 happy path。

## 冻结与追加（R-18）

- 用例写进 `cases.md`（复制 `assets/cases-template.md`），落盘后算 `Get-FileHash -Algorithm SHA256`，取前 16 位写进 `report.md` 首部
- 冻结之后**才允许**开页面、打接口；**采集阶段仍不读源码**，字段名从接口返回 / 表结构 / 需求里拿（R-20 盲采集）
- 判定写完才允许读源码定位根因；读过源码的条目在证据列标「已读源」，M2 / M3 判定降一档
- 执行中发现漏测：只在「中途新增」节追加，写新增原因，重算哈希并在报告并列第二组
- 已冻结的行不许改期望、不许删用例；收尾脚本复核哈希，不一致 = 本轮作废

## 期望值先行（借 TDD 的红灯，R-16）

用例的价值在「期望」，不在「实际」。顺序错了，测出来的只是**说明书**，不是**验收**。

### 三条硬要求

1. **执行前写死**：期望值必须在动手点页面前写进报告第二节。允许写「待验证」的只有一类——口径本身要业务拍板，且必须在报告首部「假设」里列明。
2. **期望必须可判定**：`显示正常` / `数据正确` / `符合预期` 不算期望。要么给数（`1,234,567.89`），要么给关系（`= 上游三张表之和`），要么给规则出处（`AGENTS.md 第 x 条：金额保留两位`）。
3. **来源必须标注**：四选一，写进「期望来源」列。

| 期望来源 | 用法 | 例 |
|---|---|---|
| 需求原文 | 需求 / plan 里写死的公式、取值、文案 | `plan 第 3 节：毛利率 = (收入-成本)/收入` |
| SQL 反算 | 数据对账类，先查库算出期望数 | `SELECT SUM(amount) ... → 8,642,100.00` |
| 规范条款 | 交互 / 样式 / 权限的规则出处 | `<project-rules>/report-table：数值右对齐` |
| 已知基准 | 改造前的当前值、旧系统截图、历史版本 | `改造前页面 2026-09 值 1,024` |
| 用户口述 | 只有业务方能定的口径，须记时间 | `用户 2026-10-23：新老客按首单年算` |

> **这五个词之外的都不算依据。** 尤其禁用「源码」「实现」「代码里是这么写的」——
> 只能引源码才成立的验收点，是实现的说明书，不是验收点：删掉它，回去确认需求（R-17）。

### 实际≠期望时怎么处理（顺序不能颠倒）

1. **先定性**：是产品缺陷（保留期望，报 P0/P1/P2），还是自己期望写错（口径理解错、公式抄错、取错了基准）
2. **判为期望写错**：原期望**保留不删**，在同一格并列写 `~~原期望~~ → 更正为 X，依据：<出处>`
3. **禁止动作**：把实际值抄进期望列、删掉原期望只留新值、改成「以实际为准」

> 这一条来自真实漏网：批注「清空即删除」未生效，因为当时是**看完实际行为后才补的期望**，等于把 bug 写成了预期。

### 数据对账类强制顺序

先 `SELECT` 算出期望数 → 再打开页面读数 → 比对。**不许先看页面再倒推 SQL 去凑数**（凑出来的 SQL 天然对得上，等于没验）。

## 反模式

- 一个用例断言三件事（失败时定位不了）
- 只测 1 和 100，不测 0 和 101
- 用「随便填个值」代替等价类
- 边界只取上界不取下界
- 成对组合当全排列做，跑不完就放弃
- **先跑再看，把实际值写成期望**（最隐蔽，且会掩盖真 bug）
- 期望写成「正常」「正确」「没问题」这类无法判定的词
